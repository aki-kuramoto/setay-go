# setay パス記法 (設計メモ, 進行中)

> これは**進行中**の設計ドキュメントです。決定済みの点と未決の論点を分けて記録します。
> 実装 (internal/setaypath/path.bp) はまだこの決定を反映していません。

## 決定: setayq とは別物にする

setay 本体のパス記法 (Document の `Get`/`SetRaw` 等で使うアドレス表記) は、setayq
(jq 風フィルタ) のパス構文とは**意図的に別物**とする。setayq を踏まえつつ、setay に
相応しい独自の記法を定める。

### 理由

- **目的が違う**。setayq はクエリ/変換ツール。setay のパスは「単一の要素を指して
  読み書きする」アドレス表記。
- **setay の思想** (美学 §0): 世間の標準ではなく setay の意図した挙動が正。jq のパスを
  そのまま入れない。
- **jq のパスには JSON/jq 由来の癖**がある。

### 関係の注意

「なんとなく似ているが微妙に違う」は最悪の UX。別物にするなら、意図的に十分違えるか、
関係を明記すること。

## 記法の形 (決定済み)

パスは `:/` で始まり、以降は `.` 区切りのセグメント列。各セグメントは bare key /
引用キー / 数値インデックスのいずれか。

例 (実在の想定):

```
~/.app-data/u2/config/key-bender.setay:/underlay-definitions.for-daiv-internal-japanese.override-specs.0.as
```

`key-bender.setay:/` までがファイルとその中身への入り口、`:/` 以降が setay パス
(`underlay-definitions` → `for-daiv-internal-japanese` → `override-specs` → 添字 `0`
→ `as`) で、末尾は値 `"left-ctrl"` を指す。

### 先頭 `:/` (root マーカ, 単一トークン)

- パスは `:/` で始まり、setay 文書の root を表す。
- `:/` は**単一トークン**。`: /` のように間に何かが入ったものは `:/` と見做さない。
- FS ブラウザとの合成は「左のものの中身に入る」演算子として連鎖する。ファイルが zip 内
  なら `~/.app-data/bk.zip:/u2/config/key-bender.setay:/...` のように `:/` が複数現れる。
  setay パスの `:/` は特別な合流規則を持たず、この連鎖の一段にすぎない。

### ステップ区切りは `.`

- セグメントは `.` で区切る (`:/a.b.c`)。
- **末尾区切り `:/a.` や空セグメント `:/a..b` は無意味 → 不正 (reject)**。

### bare key = LenientIdentifier、それ以外は必ず引用

- 裸で書けるキーは LenientIdentifier に一致するものだけ (先頭・末尾ハイフン不可、
  中間ハイフン可)。setay.bp の `SetayBareKey` / boompaw.bp の `LenientIdentifier`。
- **LenientIdentifier に一致しない全てのキーは `"` か `'` で囲う**。
- `/` や `:` を特別視しない。「LenientIdentifier か否か」だけで引用の要否が決まる
  (結果として `/` や `:` を含むキーは引用されるが、それは一般規則の帰結にすぎない)。
- 大文字小文字は区別する。

### インデックスは数値の dot セグメント

- リストの添字は `.0`, `.1` のように数値セグメントで表す。ブラケット `[n]` は使わない。
- 負値も可 (`.-1`)。`-` は識別子の先頭になれない (先頭が `-` のものは演算子か負数
  リテラル) ので、`-1` は曖昧なく負数。

### Set の降り方 = 重複を許さない List

Set は「値を持たない Dict」ではなく「**重複を許さない List**」として降下する
(数値インデックスで降りる)。

### UtcTs は当面は終端、将来の降下の道を残す

現時点では UtcTs は終端スカラ。ただし将来、埋め込まれた TZ / 時 / 分 / 秒 のような
要素へ降りられる余地を**閉ざさない**定義にする。

### 現段階は単一値のみ (暫定)

**現段階では**単一値のみを指す (ワイルドカード/グロブ/スライス無し)。これは「複数
マッチを永久に排除する大方針」ではなく、現段階の割り切り。複数マッチは setayq の領分。

## 文字列・エスケープは Balzak に従う (Setay ⊂ Balzak)

JSON が JavaScript の派生サブセットであるように、**Setay は Balzak のサブセット**に
したい (`boompaw/project-balzak`)。よって引用キーの文字列・エスケープ記法は、setayq でも
今回の試作 path.bp でもなく、**Balzak の文字列リテラルに従う**。Balzak は未完で、現行の
リテラル定義には既知の誤りがあり修正予定なので、ここは Balzak 側の確定を待つ。

## 構造編集の考え方 (パスの役割)

CST をオブジェクトとして直接弄る。パスの役割は「弄り始める基準ノードを素早く見つける」
こと。挿入位置などをパスで表す必要はなく、**見つけたノードに対する操作** (例:
appendBefore / appendAfter / rename / delete、コンテナへの append / prepend) が担う。
その為にパスは、値だけでなく **キー / エントリ / コンテナも指せる**必要がある
(空コンテナへ append する為にはコンテナ自身を指せる必要がある)。

## 未決の論点 (一つずつ決める)

- **キー / エントリ / コンテナの指し分けの具体表記**。既定はそのセグメントの「値」。
  「キー自体」や「エントリ (キー+値)」をどう書き分けるか (末尾マーカ等) は未決。
- **引用キーの最終エスケープ**。= Balzak 文字列に依存。Balzak 側の確定待ち。
- **構造編集操作の API 形**。パスではなく操作側 (appendBefore/After, rename, delete,
  append/prepend) の設計。別途。
