# Setay の美学と正しさ (ドラフト) 

Setay は設定ファイルの記述を最大の目的として設計されています。
YAML / TOML の桁に意味を持たせる記法は壊れやすく, 私には扱いづらく感じられるものでした。
かといって JSON は「情報交換の為のフォーマット」なので, 設定ファイルの記述には向かない部分があり, 「情報交換の為のフォーマット」という役割を考慮すれば「安易に変更を加えるべきではない」という意見に納得もできるのです。
これらの理由から, JSON 的でありながら, 設定ファイルを第一の目的とした専用のフォーマットがあってもよいはずだと思われました。

この文書は Setay が「何を美しいとするか (整形の美学)」と「何を正しいとするか (意味論の厳密さ)」を言語化します。

---

## 0. 大前提 — 実装された挙動こそが仕様

Setay の「正しさ」には昨今の標準や慣習と食い違いがあります。
まだ設計者の意図通りでない挙動も多いものの, 既存の挙動の多くは Setay としての美学を表明しており, 外部の「普通」と違うからといって即座に上書きされるべきものではありません。

---

## 1. インデントはタブ, 行内の整列は空白

- **行頭のインデントにはタブを使う** (空白ではない)。ネスト1段につきタブ1個。
- **タブは行頭のインデント専用**。行頭から一度でもタブ以外の文字が現れた後はタブを使わない。その後で整形 (区切りや整列) が必要なら, そこには **空白** を使う。

タブは, 個々人に与えられた自由の象徴です。
タブを何文字幅に設定するかは, 表示する人に与えられた自由です。
設計者に言わせてもらえば「世界は空白 N 文字でインデントされているべきだ」というのは全体主義的な発想です。

この自由が成立する条件として, 行頭からタブ文字以外の文字が現れた後には, もうタブ文字を使うべきではない, というのが経験則としてわかっています。
これに従う限り, タブでインデントする世界はそんなに悪くないのです。200X 年代くらいまでは, 世界の大部分はそれを知っていたと思います。

このわずかなルールが理解できなかった人が軋轢を起こしていた結果, いつのまにか全体主義者が自由を殺してしまい, それが当たり前になったと思います。
Setay はこの流れに抗います。それが Setay の正義です。

## 2. 空行もその深さのインデントを持つ

空行は「無」ではなく,  ** その構造的な深さを表すもの ** として扱う。深さ d の空行はタブ d 個ののちに改行する。

空き地には何もないのですか?
となりの空き地が, ただの空き地の代わりに void 空間だったら困難が多いでしょう。
インデントされた位置の空行は, 正しくその分のインデントを含んでいるべきです。

これで差分をとる時に誤った対象が選ばれる事も減ります。つまりあなたは今まで void 空間の為に無駄な苦労をしていたという事です。

## 3. ブロックと括弧

- **dict は原則的に多行**。1エントリ=1行で `key = value;` を基本とする。一行に収めた方が適切だと判断した場合には一行に収めてもよいが, これには絶対的な基準は存在せず, 感覚に依存するもので, 基準を定量化はできない。
- **中身のある dict を値にするとき, 開き `{` は単独行に置き, キーと同じ深さに揃える**
   (いわゆる Allman 風) 。`key = {` と同じ行に始めない:

```setay
key =
{
	inner = 1;
};
```
理由は視覚的に構造の確認が容易である事。
zigzag スタイルだと縦方向に表示を節約できるという考え方もあるが, その判断は画面に20行くらいしか表示できなかった時代, 紙にコードをプリントしていた時代の基準を引きずっている。

- **空の dict は同一行に収めても良い `{}`** (`key = {};`) 。これは上記の一行に収めた方が適切だと判断した場合の一例である。しかし一行に収めず分割して書いても良い事を忘れない事。次のように書けば, これから中身を足すつもりだという意図が残り, 末尾区切りと同じ理屈で diff も自然になる:

```setay
hoge =
{
};
```

## 4. リスト — 短ければ1行でもよく, 多行展開するなら1要素1行 (括弧の位置ルールは dict と共有する)

- **リストの `[` は `{` と同じ位置ルールを共有する**。多行にするなら, 開き `[` を単独行に置き, キーと同じ深さに揃える (Allman 風)。これが標準:

```setay
hoge =
[
	1,
	2,
	3,
];
```

- **短く単純なリストは1行に収めてもよい**。角括弧の内側の余白 (padding) は有っても無くてもよい:

```setay
hoge = [1, 2, 3];
hoge = [ 1, 2, 3 ];
```

- `key = [` と同じ行から多行を始める書き方は **標準ではない (逸脱)**。ただし構文としては妥当であり, 逸脱する自由の為に許容される:

```setay
hoge = [
	1,
	2,
	3,
];
```

- **長い / ネストを含む / コメントを含むリストは多行にする事を検討するべき**。
- **単一行にできるかの目安はない。**。
- ネストした dict/list を含むリストは多行にする事を検討するべきだが, それもその要素次第である。
- 1要素1行の時, 閉じ `]` は開き `[` の深さに揃える。

## 5. 末尾の区切り

- **多行では最後の要素にも区切りを付けるべき**。
  dict の各行は `;`, list の各要素は `,` (最後も)。
  list でも多行の場合には末尾の `,` を推奨する理由は追加・削除が対称になり, 差分が綺麗になる為。
- **単一行リストには末尾カンマを原則としては付けない** (`[ 1, 2, 3 ]`) 。

## 6. 値は表現型を尊重する。真偽値と null は「予約語」なので正準の語に揃える

- **数値は書かれたまま保存**。`0x0A` を `10` に正規化しない。基数・桁・プリフィックスは記述者の意図の一部として扱う。
- **文字列も原文のまま** (クォートの種類・エスケープは理由なく変更しない)。
- **キーの表現も逐語** (裸キーは裸のまま, クォート付きはそのまま)。
- ただし **`true` / `false` / `null` は正準の小文字語に統一**。これらは「予約語」であり, `True` も `TRUE` も, 当然 `TRuE` も true ではない。

## 7. コメントは一級市民

- **コメントを保存し, 構造に合わせて再配置する**。これは JSON にできないことであり, Setay が JSON でない理由の一つ。
- 形式: `# ` (ハッシュ+空白) , `#\t` (ハッシュ+タブ) , `##`, `#!` (shebang 回避) , `#{ … }#` (複数行) , そして `#`+改行/EOF (空コメント) 。
- **`#` の直後は 空白 / タブ / `#` / `!` / `{` / 改行 のいずれかでなければならない**。
  `#foo` はコメントではない。これは将来的な拡張の為の意図的な予約である。
  そもそも Setay におけるコメントは **ディレクティヴの一部** である。`#foo` は意地悪で拒否されるのではなく, 正しいディレクティヴの記法に沿っていない為に拒絶される。

## 8. 数値の正しさ — 曖昧さを排する

- 基数は **明示プリフィックス**で表す: `0x` (16進) , `0b` (2進) , `0o` (8進) , `0d` (明示的10進) 。
- **先行ゼロは10進として解釈** (8進ではない) 。暗黙8進という慣例には実利がない。
  8進数で表したいなら `0` よりも `0o` くらい明示的なプリフィックスのほうが人類の共通のセンスに合っている。
  実利がない慣例を物知り顔で若者たちに強要するのは悪い意味でのオタクくさい。
- 思想: `0d` も用意しているのは明示したい場合には明示する方法を与える為。「それは必要ない」と断言する人は、16進法で書かれる事が多いものが10進法で書かれている時 (コードポイントなど) の曖昧さを想像するべき。明示できた方がいい場面はいくらでも実在する。

## 9. 型と構造

- **トップレベルは常に dict** (`{ … }`) 。任意の値をトップに置けるのではなく文書は必ず dict である (root は `SetayDict`)
  - これは本当に様々な可能性を考えて迷った中での決断である。当初はトップレベルの `{` と `}` は省いて記述できた方が、より設定ファイルとして使いやすいかもしれない等の可能性も検討していたが、実利に対して複雑さの増大が割に合わないと判断した。
    常に dict を root として、且つそれは記号としても明示される。必要以上の複雑性を呼び込まない為の判断結果がこの形である。
- **UtcTs(…)** を第一級の時刻型として持つ。これは「地球上の話をしている限り、ローカル時間は UTC とタイムゾーンから導き出すほうがいい。日常生活では相対性理論までは気にする必要はない。」という単純な話が一向に伝わらない層がたくさんいる事への対応策である。
- **Set** `{ key=; … }` (`=;` は原子トークン, 間に空白を入れない) 。集合が何を許さないかを表現する上で、リストに寄せるよりも dict に寄せた表記のほうが感覚と一致するという理由である。
- **変数参照** `${VAR ?: fallback}`。フォールバック連鎖を持てる。
  - これは「設定ファイルを記述する為のフォーマット」であり、情報交換の為の汎用のフォーマットではないから導入できるもの。
  - なんでもできる道具は、なにをやるにもやりづらいもの。道具は明確な目的に対して最適化したもののほうが使いやすい。「汎用」は何も失いたくない為に全てを失っている状態。

## 10. なぜ JSON でも YAML でも TOML でもないのか 

- **JSON**: コメントが書けない。末尾カンマを許さない。汎用の情報交換フォーマットと定義されてしまった為、安易な変化がその役割を損ねるという意味で、その不自由さが妥当。
  Setay は「設定ファイルの為のフォーマット」に振り切っているのでコメントが一級で末尾区切りもありなし両方を許容。互換性についても過去のものが読めたら充分であり、拡張に対しては常に開かれている。
- **YAML**, **TOML**: 意味を持つ空白 (インデントが構文) で fragile に感じる。触る時にびくびくしないといけない。
  Setay の構造は全部 printable

## この文書の位置づけ

Setay には明確に「今の当たり前に対して物申す」意図がある (現状の世界に何一つ不満がないなら Setay はうまれていない)。
一方で LLM agents は「当たり前である事が唯一のよりどころ」なので Setay が意図的に選んだ事を「過ち」として修正しようとする。
これに対応する方法として、Setay が何を正とし、何を美しいとしているかを示す必要があった為にこのドキュメントは書かれた。
